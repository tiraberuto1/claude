# 資料からの設計書作成とレビュー

依頼: $ARGUMENTS

指定された資料から設計書を作り、完成後に別のエージェントでレビューさせ、指摘を反映するまでを進める。作成とレビューは必ず別々のサブエージェントに任せ、メインの会話では設計書を書かない・レビューしない。

## 1. 依頼の整理
依頼から次を取り出す。
- 資料の一覧（ファイルパス、ディレクトリ、URL）
- 設計の対象（何を設計するか）
- 資料の優先順位の指定、保存先の指定（あれば）

資料が1つも指定されていない、または設計の対象が読み取れない場合は、サブエージェントを呼ぶ前にユーザーに尋ねる。指定されたパスが存在するかは `ls` で確認し、存在しないものがあればユーザーに伝える。

## 2. 作成
`design-doc-writer` サブエージェントを呼び、次を渡す。
- 資料の一覧（パス・URLをそのまま列挙する）
- 設計の対象と、ユーザーの依頼文の原文
- 資料の優先順位、保存先（指定があれば）

writer の報告から、設計書のパス・読めなかった資料・未決事項を控える。読めなかった資料があれば、先へ進む前にユーザーに伝える。

## 3. レビュー
`design-doc-reviewer` サブエージェントを**新しく**呼び、次を渡す。
- 設計書のパス
- 資料の一覧（writer に渡したものと同じ）
- ユーザーの依頼文の原文

writer の報告内容（要旨や矛盾の解決など）はレビュアーに渡さない。レビュアーが設計書と資料だけを見て独立に判断するためである。

## 4. 判定に応じた改訂
| 判定 | 次の行動 |
|---|---|
| 差し戻し | writer にレビュー結果の全文を渡して改訂させ（改訂モード）、手順3で再レビューする |
| 条件付き承認 | writer にレビュー結果の全文を渡して改訂させる。「要再レビュー」の指摘があれば手順3で再レビューし、なければ再レビューしない |
| 承認 | Minor / Nit があれば writer に渡して改訂させる。なければ終了 |

レビューは最大3回までとする。3回目でも差し戻しなら、残っている Critical を添えてユーザーに判断を仰ぐ。

改訂のたびに、writer が「対応しない」とした指摘とその理由を控える。

## 5. ユーザーへの報告
次を簡潔に報告する。
- 設計書のパス
- レビューの経過（回数と各回の判定、指摘件数）
- 最終判定
- writer が対応しなかった指摘とその理由（あれば）
- 資料間の主な矛盾と、その解決
- ユーザーに判断してほしい未決事項（選択肢と推奨案つき）。決定が出たら writer で設計書の「決定」欄を更新できることを添える
